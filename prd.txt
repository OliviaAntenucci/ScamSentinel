================================================================================
ScamSentinel: Product Requirements Document
================================================================================
Version: 0.2
Date:    2026-10-14
Status:  MVP complete (M0-M6 done)

--------------------------------------------------------------------------------
1. SUMMARY
--------------------------------------------------------------------------------
ScamSentinel is a portfolio cybersecurity project: a local, explainable
scam and phishing analyzer that is itself threat-modeled and tested as an
attack surface. It takes a suspicious SMS, email, URL, or screenshot and
decides whether it is a scam. Every verdict comes with human-readable,
evidence-backed reasons.

Detection is organized into scam categories, each with its own trusted
facts, signals and labeled test data. The MVP covered tax-season
impersonation (IRS, TurboTax, QuickBooks, Credit Karma), which remains the
baseline. Package-delivery smishing (USPS) was added after the MVP (G1).

Design principle: "The LLM extracts, the rules decide." No verdict depends on
an opaque model output alone.

--------------------------------------------------------------------------------
2. PROBLEM
--------------------------------------------------------------------------------
- Tax season brings a spike in phishing that impersonates the IRS and tax
  software vendors: refund "verification" links, account-suspension texts,
  and fake payment demands.
- Most consumers can't tell irs.gov from irs-gov-refund.com, or turbotax.com
  from turb0tax.com.
- Generic spam filters give a score with no explanation. Users and analysts
  need to know WHY something is a scam so they can trust the result and
  learn from it.

--------------------------------------------------------------------------------
3. USERS & USE CASES
--------------------------------------------------------------------------------
U1. Taxpayer: "I got a text saying my refund is on hold. Is this real?"
    -> Paste text, get a verdict and plain-English reasons.
U2. Security analyst: "Triage this reported phishing email or link."
    -> Submit a raw .eml or URL, get structured JSON for a ticket.
U3. Developer / evaluator: "How accurate is this?"
    -> Run the eval harness and get precision, recall, F1, and FPR.

--------------------------------------------------------------------------------
4. GOALS / NON-GOALS
--------------------------------------------------------------------------------
Goals (MVP)
  G1. Correctly classify tax-themed scams across text, email, URL, and image
      inputs.
  G2. 100% of verdicts include at least one evidence-backed reason (or an
      explicit "no risk signals found").
  G3. The tool resists prompt injection and malicious uploads, never
      connects to user-supplied URLs (no SSRF by design), and tests
      demonstrate each defense.
  G4. Measured, reproducible accuracy on a held-out labeled test set.
  G5. Runs on a laptop in a Python virtual environment. No Docker, no
      headless browser.

Post-MVP goals: proactive lookalike discovery via Certificate Transparency
logs, and inspecting live phishing pages. See section 10.

Non-goals: see SCOPE.md.

--------------------------------------------------------------------------------
5. MVP DEFINITION
--------------------------------------------------------------------------------
The MVP is done when someone can run ScamSentinel on their own computer,
send it a text message, email, URL or screenshot from the command line, and
get back an explainable verdict, with the security defenses tested and
accuracy measured. That is milestones M0-M6 (section 10).

--------------------------------------------------------------------------------
6. FUNCTIONAL REQUIREMENTS (MVP)
--------------------------------------------------------------------------------
Input handling
  FR-1   Accept plain text (SMS / chat), up to 20,000 characters.
  FR-2   Accept a raw email (.eml, RFC 5322) up to 2 MB. Parse headers
         (From, Reply-To, Return-Path, Authentication-Results), text/plain
         and text/html bodies. Never render HTML. Never open attachments.
  FR-3   Accept a URL (http/https). Analyze it as a string with the domain
         engine and verification layer. NEVER fetch it.
  FR-4   Accept an image screenshot (PNG/JPEG/WebP) up to 5 MB and 25 MP.
  FR-5   Extract all URLs and domains from text/email/OCR output, including
         defanged forms (hxxp://, example[.]com), and analyze each.

Lookalike-domain engine (done, M1)
  FR-6   Reduce every host to its registrable domain using the Public Suffix
         List. "turbotax.com.evil.net" must resolve to "evil.net" with
         "turbotax" flagged as a subdomain brand token.
  FR-7   Decode IDN/punycode (xn--) and compute a Unicode confusables
         skeleton (UTS #39), plus ASCII lookalike classes (0->o, 1/i->l,
         5->s, rn->m, vv->w, ...).
  FR-8   Compute normalized edit distance (Damerau-Levenshtein) between the
         label and each protected brand token.
  FR-9   Detect brand-token containment plus keyword stuffing (verify,
         secure, refund, claim, login, account, update, support, tax,
         etc.) and hyphenated compounds.
  FR-10  Exact matches against the official allowlist (e.g. irs.gov,
         intuit.com, creditkarma.com, and their subdomains) return
         "official" and score 0 for the domain module.
  FR-11  Output: score 0-100, matched brand, technique(s) fired, and the
         normalized form, for explainability.

Message analyzer
  FR-12  A deterministic keyword/regex extractor finds urgency, payment
         methods, sensitive-data requests, threats, brand mentions,
         injection phrases, phone numbers and URLs.
  FR-13  The LLM (Groq by default, Claude optional) returns a strict JSON
         schema: urgency (0-10 + quoted spans), impersonated_entity,
         payment_methods[], sensitive_requests[], claimed_urls[],
         call_to_action, threats[], and injection_attempt (bool + span).
  FR-14  Each LLM-extracted signal must quote a verbatim span from the
         input. Signals whose span does not appear in the input are
         discarded (hallucination guard).
  FR-15  If the LLM is unavailable or returns invalid output, the system
         degrades to rules-only and says so in the response.

Verification layer
  FR-16  Check claims against a curated trusted-facts store, including:
         - Official domains per brand.
         - "IRS does not initiate contact by email, text, or social media
            to request personal or financial information."
         - "IRS does not demand payment by gift card, crypto, or wire."
         - Official phone numbers (IRS, Intuit support) where published.
         - Email sender alignment (display name vs. sending domain).
  FR-17  Each check yields {check, claim, verified: true|false|unknown,
         source}.

Screenshot analysis
  FR-18  Validate the header (type, size, pixels), sanitize at the byte
         level (strip metadata and anything after end-of-image; no local
         decoding), transcribe with a Groq vision model (timeout), then
         pass the text through FR-5 and FR-12-FR-15. If the image can't be
         read (no key, vision failure, no text), return an error, never a
         verdict.

Aggregation & output
  FR-19  Combine module scores with configurable weights, renormalized over
         the modules that ran. Critical overrides (e.g. SSN request plus a
         lookalike link; IRS plus gift-card demand) set a minimum score.
  FR-20  Verdict bands: 0-29 likely_legitimate, 30-59 suspicious,
         60-100 likely_scam.
  FR-21  Response includes verdict, risk_score, per-module scores,
         reasons[] {module, signal, detail, evidence, points}, modules_run,
         degraded flags, and analysis_id.

Evaluation
  FR-22  The dataset has train/dev/test splits with fixed seeds. Test is
         never used to tune weights, thresholds, or prompts.
  FR-23  Report precision, recall, F1, FPR, and the confusion matrix,
         overall and per input type and per brand.
  FR-24  Report ablations: rules-only vs. LLM+rules; with and without the
         verification layer.

--------------------------------------------------------------------------------
7. NON-FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------
  NFR-1  Explainability: every point in risk_score traces to a reason.
  NFR-2  Latency (p95, local): text/URL/email < 4 s; screenshot < 10 s.
  NFR-3  Security: see SECURITY.md. Upload, injection, no-fetch and
         local-API tests pass in CI.
  NFR-4  Privacy: analyses are kept for at most 7 days by default. SSN-like
         and card-like numbers are redacted before logging. Nothing is
         sent to the LLM beyond the input text.
  NFR-5  Determinism: given the same LLM features, scoring is fully
         deterministic and unit-testable.
  NFR-6  Cost: at most one LLM call per input (two for a screenshot:
         transcription + feature extraction); responses are cached by
         content hash. Works on Groq's free tier. Since G1, one more
         call when a message names an organization without curated
         facts and contains links (the organization fact check,
         architecture.md section 17); cached by organization name.
  NFR-7  Abuse resistance: per-client rate limit (e.g. 30 analyses/min).
  NFR-8  Portability: runs in a Python virtual environment on a laptop.
         Nothing else to install; screenshots use a Groq vision model.
  NFR-9  Interface: API-only, no web UI. The API listens on
         127.0.0.1:8000 and isn't reachable from other machines. Users
         interact from the command line (curl or similar). Responses are
         JSON.

--------------------------------------------------------------------------------
8. API (MVP)
--------------------------------------------------------------------------------
  POST /v1/analyze           JSON {text | url | email_raw}
  POST /v1/analyze/image     Raw screenshot body (image/png|jpeg|webp)
  GET  /v1/analysis/{id}     Fetch a stored result
  GET  /v1/domain/score?d=   Domain engine only (done)
  GET  /healthz              Status, LLM provider/model, key configured
  GET  /v1/ct/candidates     Post-MVP P1: lookalikes found in CT logs
                             (?since=&min_score=&limit=)

--------------------------------------------------------------------------------
9. SUCCESS METRICS / ACCEPTANCE CRITERIA (MVP)
--------------------------------------------------------------------------------
  AC-1  Held-out test set: F1 >= 0.85 and FPR <= 5% on legitimate tax
        messages. (These are targets. README reports the measured values,
        whatever they turn out to be.) Measured 2026-10-15 (scoring v2) on
        the 30-sample synthetic test split: F1 93.3%, FPR 0% rules only;
        F1 100%, FPR 0% with the Groq LLM. Met, with the caveat that the
        data is small and hand-written (see README).
  AC-2  Domain engine: >= 95% recall on a generated lookalike suite
        (homoglyph, typo, keyword-stuffed, subdomain-abuse, IDN) and 0
        false positives on the official allowlist. (Met: 100% on the
        generated suite.)
  AC-3  Analyzing any URL, including every payload in
        tests/security/ssrf_payloads.txt, makes no outbound connection.
  AC-4  Prompt-injection suite: no injected sample lowers its verdict band
        compared with the same sample without the injection.
  AC-5  Upload suite: all malformed/hostile files are rejected or safely
        processed with no crash, hang, or resource exhaustion.
  AC-6  100% of responses contain >= 1 reason.

10. MILESTONES
--------------------------------------------------------------------------------
MVP
  M0  Docs, repo skeleton, API skeleton, test harness          (done)
  M1  Lookalike-domain engine + unit/property tests             (done)
  M2  Message analyzer (rules first, then Groq) + verification  (done)
  M3  Aggregator + POST /v1/analyze (text, URL, email) + storage  (done)
  M4  Security hardening: upload guard, prompt-injection suite,
      no-fetch test, log redaction, rate limit                  (done)
  M5  Screenshot analysis (Groq vision transcription)          (done)
  M6  Eval dataset + harness + published metrics               (done)

Post-MVP (in order, only after M6). E1-E4 ("explain and guide") deepen
the tax-scam niche and explainability, and come before page fetching.
  P1  Certificate Transparency watcher (crt.sh) + GET /v1/ct/candidates
                                                                (done)
  G1  Brand-agnostic core + scam categories: brands, categories, facts
      and phrases are data; the LLM schema, verification and floors
      read them. Package delivery (USPS) as the second category, with
      sourced facts, 39 samples and its own metrics.              (done)
  G2  Bank impersonation (Chase, Bank of America, Wells Fargo) with
      sourced facts, 39 samples and its own metrics.              (done)
  G3+ One new category at a time (account takeover, tech support,
      job scams), each with sourced facts, signals, hard negatives
      and separately reported metrics.
  E1  "What should I do next?": evidence-based, cautious next steps
      from fixed templates (never repeats links/numbers from the
      message; official contacts only from facts.yaml)            (done)
  E2  Richer domain explanations (swapped characters, misspelling,
      misleading extra words, real owner of the domain)          (done)
  E3  Fact-check summary: claims that match / conflict / can't be
      verified against trusted facts, with sources                (done)
  E4  Named scenarios per category (refund delay, payment demand,
      package on hold, ...), added over time as data              (next)
  P2  Lightweight page fetch (httpx + HTML parser) + SSRF URL guard
  P3  Playwright headless-browser sandbox in an isolated container
  P4  Docker packaging

--------------------------------------------------------------------------------
11. RISKS & OPEN QUESTIONS
--------------------------------------------------------------------------------
  R1  Public phishing feeds (PhishTank, OpenPhish) are mostly URLs with few
      tax-themed message bodies. Synthetic data fills the gap but may
      inflate scores. Mitigation: report results on real vs. synthetic
      samples separately.
  R2  Without page fetching, the MVP can't see what's behind a clean-looking
      link (e.g. a URL shortener). Mitigation: message and verification
      signals still apply; page analysis is post-MVP (P2).
  R3  LLM free-tier rate limits or model changes. Mitigation: caching,
      rules-only fallback, provider is a config setting.
  Q1  Is VirusTotal / Google Safe Browsing enrichment worth the API
      dependency (post-MVP)?
